# v3.2.0 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:subagent-driven-development` (or equivalent `claude-mem:do` pipeline) to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.
>
> **Mandatory consultations:**
> - **`ui-ux-pro-max` skill** — invoke before AND after any markup/CSS edit on every UI-bearing task (#345, #342, #343, #344, #346, #347, #348, #349 — i.e. every task in v3.2.0). v3.2.0 is the admin-UX milestone; **every PR is UI-bearing** and must pass the design-language gate.
> - **`documentation` skill** — invoke for every doc edit (`docs/*.md`, `CHANGELOG.md`, `README.md`, `mkdocs.yml`, the living-doc).
> - **Memory MCP** — `add_observations` to `project:simple-php-ipam:release:v3.2.0` (create the entity on Task 0) at the close of every task. Required fields per CLAUDE.md: factual sentence, files touched, git short hash, test result.
>
> **No deferrals without explicit user approval.** Every issue listed below ships in v3.2.0. If a finding cannot be addressed in the current task, surface it before continuing — do not silently push to "later".

**Goal:** Ship v3.2.0 covering all 8 milestone-24 issues (#342–#349) — admin chrome adoption, cookie-session login form, logout, sidebar, audit-log polish, TOTP enrol/disable, API-keys revoke + post-mint display, and a Settings page that surfaces ~20 config knobs — under one unified design language with complete docs.

**Architecture:** Sequential PR fan-out off `release/v3.2.0`, modelled on v3.1.0's PR1–PR10 pattern. Each issue is its own PR; all PRs merge into `release/v3.2.0`; the final release-cut PR opens `release/v3.2.0 → main`. **#345 (chrome) ships first** because it unblocks every other admin-page change. Authentication (#342, #343) ships next so the sidebar (#344) and remaining pages can rely on a real cookie session for the signed-in username. Polish/feature work (#346–#348) follows. The Settings page (#349) is largest and ships last so it can attach to the finalised chrome + sidebar + audit-badge work. Release cut closes the milestone.

**Tech Stack:** PHP 8.2+ (strict types, GMP), SQLite3, plain JS + BigInt, mkdocs + spectral, PHPUnit 11, Playwright 1.4x via docker, PHPStan L9, PHPCS PSR-12 (+ `.phpcs-admin.xml` template-aware ruleset from v3.1.0), Semgrep.

### CodeRabbit policy

Every PR triggers CR review. Fix every actionable finding (Critical / Major / Minor) before merging — do not dismiss. Nitpicks may be deferred only if explicitly approved.

### UI design-language gate (every task in v3.2.0)

Before AND after every markup/CSS edit on every task in v3.2.0:

1. Invoke `ui-ux-pro-max` skill with the changed surface as input.
2. Confirm parity with the v2.9.0 style guide (`docs/superpowers/plans/2026-04-25-v2.9.0-ui-ux-style-guide.md`):
   - Teal accent (`--color-accent: #06d6a0`); dark-text on teal buttons.
   - Tool-drawer pattern for any "result-with-form" surface.
   - `help_bubble()` for any non-obvious control.
   - `@media (hover: none)` action sheet for any drag-or-hover-dependent affordance.
   - Focus-visible outline (2px accent) on every interactive element.
   - **Admin-specific:** every admin page must look like part of the calculator — same header, same single-card surface (#345), same input/button tokens, sidebar lives outside the card content area (#344).
3. Document the consultation output verbatim in the PR description.
4. If the consultant flags any deviation, fix in the same task. **Do not defer.**

### Documentation gate

Every doc edit goes through the `documentation` skill before commit. Required reviews:
- Accuracy against current code behaviour.
- No internal/server config secrets documented.
- Consistent voice and terminology with `docs/index.md` and `mkdocs.yml`.
- New admin-facing doc pages (`docs/admin-login.md`, `docs/admin-settings.md`) added to `mkdocs.yml` nav.

### Test rig

The `_test-drain.php` endpoint shipped in v3.1.0 (#324) zeroes admin state at suite setup. Every admin-touching test in v3.2.0 must run AFTER the drain. New admin DB tables introduced in this milestone (`admin_sessions`, `admin_state`, plus migrated columns on `admin_recovery_codes` and `api_keys`) MUST be added to the drain script in the same PR that introduces them.

1. Admin pages render exactly one outer `.card` — sub-sections are dividers, not nested cards.
