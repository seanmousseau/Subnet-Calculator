# v3.2.0 Task 6 (#347) — TOTP enhancements — ui-ux-pro-max BEFORE consult

Date: 2026-05-05
Subject: `/admin/totp.php` rewrite — three sub-sections (Status / Enrol-or-Recovery / Disable) under the existing single `.card` admin shell. Issue #347.

This is a BEFORE consult — design guardrails captured before any code edits, applied
verbatim during implementation, then re-validated in the AFTER consult against the diff.

## Locked context

- The admin shell renders one outer `.card` per page (cross-cutting rule for v3.2.0). Sub-sections are dividers, not nested cards.
- Tokens already in `assets/app.css`: `.badge-active`, `.badge-revoked`, `.alert-error`, `.alert-success`, `.alert-accent`, `.api-key-display`, `.splitter-btn`, `.btn-danger`, `--color-accent`, `--color-error`, `--color-bg`, `--color-surface`, `--color-text`, `--color-border`, `--color-btn-text`. Existing admin-section divider rule lives under `.admin-card section + section`.
- The page must work in light + dark themes using existing tokens; no ad-hoc colour values.
- Three sub-sections render in this fixed order: Status → (Enrol XOR Recovery codes) → Disable (only when enabled).
- All new interactive controls inherit the existing focus-ring + 44px touch-target behaviour from `.splitter-btn`.

## Section A — Enrol sub-card layout (when `$admin_totp_secret === ''`)

### Must-have
- **Single-column stack on mobile (`< 768px`); two-column responsive grid above** — left column QR + manual-entry secret, right column 6-digit verify form. Use CSS grid with `grid-template-columns: minmax(220px, 1fr) 1fr; gap: 1.5rem;` inside the section. Mobile collapses to one column via `@media (width <= 767px)`.
- **QR rendered as inline SVG** (PHP-side QR generator on the otpauth URI, no external CDN) at a minimum 180px square so phone cameras lock at arms length. Surround with `aria-label="QR code containing TOTP enrolment URI"`. Provide a `<noscript>`-friendly fallback line directly under the QR exposing the otpauth URI as selectable text.
- **Manual-entry secret as a copy-button + monospace block.** Reuse `.api-key-display`. Pair with a `<button class="splitter-btn" type="button" data-copy-target="#totp-secret-text">Copy</button>`. The button uses the existing clipboard helper in `app.js` (no new clipboard surface). Include explicit copy-success affordance via `aria-live="polite"` text swap.
- **Verify form adjacent (right column on desktop, below on mobile).** A single `inputmode="numeric"`, `pattern="[0-9]{6}"`, `maxlength="6"`, `autocomplete="one-time-code"`, `required`, with `<label for="totp-verify-code">Enter the 6-digit code from your app</label>`. Submit button `Verify and enable`. Disable on submit (loading-buttons rule) — reuse the existing `data-busy` pattern in `app.js`.
- **Helper line under the form** explaining the verify step's effect: "Verifying writes the secret to `config-admin.php` and you can return here to mint recovery codes."

### Should-have
- A monospace SVG-only QR (no canvas) so the page works under the strict CSP without script-rendered fallbacks.
- The manual-entry secret rendered in 4-character groups (`ABCD EFGH IJKL …`) for legibility — many authenticator apps accept whitespace-stripped input, so this is purely for the human reading.

### Avoid
- A two-step "Generate → Verify" form that posts twice. Generate the secret once on first GET when no enrolment is in flight, hold it in `$_SESSION['totp_enrol_secret']`, and clear it on verify-success or on hitting the page after enrolment is already done. This keeps the QR stable across reloads and avoids the "I scanned a different secret than the one verified" footgun.
- Auto-focus on the verify input — sighted users want to scan the QR first; auto-focus jumps the page on screen readers.

## Section B — Disable sub-card placement (when `$admin_totp_secret !== ''`)

### Must-have
- **Always-visible section** below Recovery codes (NOT inside `<details>`). Hiding it implies it is hard to find when an operator legitimately needs to disable; the safety guard is the form, not the visibility.
- **Danger styling via `.btn-danger`** on the submit button (already in the token set). Section heading `<h2>Disable TOTP</h2>`. Section gets a subtle danger-tinted top border via `border-top: 1px solid var(--color-error);` and 1.5rem top padding so the divider visually separates it from Recovery codes without escalating to a nested card.
- **Confirmation copy** above the form, exact wording:
  > Disabling TOTP removes the second factor from `/admin/` login. Anyone with the admin password will be able to sign in without a code. To continue, enter a current TOTP code or an unused recovery code.
- **Single input** for the second-factor (TOTP-or-recovery, same pattern as `/admin/totp-verify.php`). Label "Authenticator code or recovery code". Reuse the `.admin-input-totp` class so the field styling matches the verify page.
- **Submit button label `Disable TOTP`** (verb-first, no "are you sure" double-negative). Add `formnovalidate="false"` and a JS `onsubmit="return confirm('Disable TOTP for this admin? This deletes all recovery codes too.')"` as a belt-and-braces guard for power users who fat-finger the form on a wide screen. The server-side flow still requires a valid second factor; the JS confirm is purely UX friction.

### Should-have
- A small italicised "_This also deletes any unused recovery codes._" line under the input so the operator knows recovery rows are dropped.
- Show the unused-code count inline ("_You currently have 7 unused recovery codes — disabling will delete them._") so the consequence is concrete.

### Avoid
- A `<details>`-wrapped Disable section. Hiding destructive controls inside collapsible UI is a known dark pattern when discoverability matters (operator support scenario).
- Two separate buttons ("Disable TOTP only" vs "Disable TOTP and clear codes"). Always-bundled keeps the auth model coherent — leaving recovery rows behind after a disable would expose stale auth material on re-enable.
- Auto-redirect to login after disable. Keep the operator on the TOTP page with a success banner so they can see the state changed; they will hit logout themselves if they want.

## Section C — Per-code list inside `<details>`

### Must-have
- `<details>` rendered inside the Status section, summary line: `<summary>Recovery codes: <strong>N</strong> unused / 10 total</summary>`. Default-closed; opening reveals a `<table class="admin-recovery-list">` with columns: `#` (row id), `Status`, `Used at`, `Used from IP`.
- **Used rows dimmed** via `opacity: 0.55;` and a `<span class="badge badge-revoked">used</span>` cell. **Unused rows** show a `<span class="badge badge-active">unused</span>`. No strikethrough — the rows are still factual, not retracted.
- **`Used at` column** uses `<time datetime="2026-05-04T12:34:56Z">4 days ago</time>` (relative + absolute via `title` attr fallback). Reuse the time-formatting helper if `audit.php` already has one; otherwise add a tiny `time_relative_short(int $ts): string` to `functions-util.php`.
- **`Used from IP` column** plain text or em-dash for unused. Treat unset (`NULL`) as `—`.
- **Plaintext is NOT shown** anywhere — the bcrypt store cannot recover it. The summary phrasing must reinforce: *"Plaintext codes are shown once at generation. The list below is for tracking which codes have been consumed; original code values are not retained."*

### Should-have
- Sort: unused first, used last — newest used at the bottom of the used group. Helps the operator skim the still-valid codes.
- A `<caption class="sr-only">Recovery code usage history</caption>` for screen-reader accessibility.

### Avoid
- Opening `<details>` by default. Most operators visit this page with no failed-recovery events; an empty-ish expanded list is clutter. The summary line carries the headline number.
- Showing the bcrypt hash, even truncated. Operators will not understand why "the first 4 chars of the code" do not match what they typed (because the stored value is a bcrypt hash, not the plaintext).

## Section D — ARIA + keyboard for `<details>`

### Must-have
- `<details>` is natively keyboard-accessible; **do not** add `role` overrides — the browser's default semantics are correct. Just provide a `<summary>` child as the first child.
- `summary` MUST contain the count phrasing in plain text (no `aria-label`) because Safari + iOS VoiceOver speak the summary text directly. The `<strong>` inside is fine.
- Provide an `id="recovery-list-details"` on `<details>` and reference it from the unused-count badge in the Status panel via `aria-describedby` so screen-reader users hear the headline number even before opening.

### Should-have
- A `prefers-reduced-motion` media query that disables the slide-down animation if Safari ever exposes one (it currently does not animate native `<details>`, but Chromium 120+ supports `interpolate-size`).

### Avoid
- Using a roll-your-own disclosure with `<button aria-expanded>` + `<div hidden>`. Native `<details>` works in every supported browser (Safari 14+, Chrome, Firefox) and is keyboard-accessible by default; replicating it adds complexity for no benefit.

## Section E — Status card visual treatment

### Must-have
- Two-line status block:
  - Line 1: `<span class="badge badge-active">enabled</span> TOTP is active for <code>{$admin_user}</code>.`
  - Line 2: `Last TOTP login: <time datetime="…Z" title="absolute UTC">{relative phrase}</time>` falls back to `Never` when `admin_state['last_totp_at']` is unset.
- **Relative + absolute pairing** — relative phrase as visible text, absolute UTC string in the `title` attribute and `datetime` attribute. Reuse the helper added in #346 (`audit.php` already wraps timestamps in `<time>`).
- When TOTP is disabled (enrol mode), Status section text is: `<span class="badge badge-revoked">disabled</span> No second factor configured. Enrol below.`

### Should-have
- A faint divider `border-bottom: 1px solid var(--color-border); padding-bottom: 1rem;` to make the section break visible even before the first user interaction.

### Avoid
- A "live" relative-time updater (JS that re-renders "12 minutes ago" → "13 minutes ago"). The page is not long-lived enough; the absolute datetime in `title` is the source of truth.

## Section F — Token reuse vs. new selectors

### Must-have (reuse, no new selectors)
- `.badge-active` for `unused` recovery rows + `enabled` status pill.
- `.badge-revoked` for `used` recovery rows + `disabled` status pill.
- `.alert-success` for the post-enrol success banner.
- `.alert-error` for verify failures + disable failures.
- `.alert-accent` for the "your new recovery codes" mint banner (carried over from existing page).
- `.api-key-display` for the manual-entry secret monospace block.
- `.splitter-btn` for the Verify button.
- `.btn-danger` for the Disable button.
- `.admin-section + .admin-section` divider — already in `assets/app.css`.

### Should-have (new selectors — minimal)
- `.admin-recovery-list` (table) — width 100%, `td` padding `0.4rem 0.6rem`, `th` left-aligned + `font-weight: 600`. Tokens only: `border-color: var(--color-border)`. **One CSS rule, ~10 lines.**
- `.admin-totp-enrol-grid` — the two-column responsive grid wrapper described in Section A. **One CSS rule + one media-query rule, ~8 lines.**
- `.admin-disable-section` — the danger-tinted top border modifier. **One CSS rule, ~3 lines.**

Anything beyond these three new selectors is over-styling — push back during the AFTER consult.
