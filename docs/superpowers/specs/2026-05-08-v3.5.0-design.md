# v3.5.0 — IPv6 Prefix Planning + Transition (Design Spec)

**Date:** 2026-05-08
**Status:** Draft (awaiting user review)
**Milestone position:** Third of four IPv6-themed minor releases. Combines
the prefix-planning items originally roadmapped for v3.4.0 (dropped when
v3.4.0 became polish/parity) with the originally-planned v3.5.0 transition
theme.

## Milestone context

The four-release IPv6 roadmap is defined in
`docs/internal/specs/2026-05-06-v3.3.0-ipv6-foundations-design.md`:

| Release | Theme | Status |
|---|---|---|
| v3.3.0 | IPv6 Foundations | ✅ shipped 2026-05-07 (`a53ad5f0e…`) |
| v3.4.0 | IPv6 Prefix Planning *(planned)* | drifted — shipped as IPv6 Polish/Architecture/Parity instead |
| **v3.5.0 (this spec)** | **IPv6 Prefix Planning + Transition** | combines the dropped v3.4.0 prefix items with the original v3.5.0 transition theme |
| v3.6.0 | IPv6 Multicast | milestone seeded; spec at its turn |

The drift wasn't recorded anywhere when v3.4.0 was scoped. v3.5.0's
combined scope is a one-shot correction: ship the dropped prefix-planning
items alongside the transition theme so the four-release roadmap closes
out cleanly at v3.6.0.

## Goal

Ship v3.5.0 — three prefix-planning tools (carry-over from v3.4.0
roadmap drift) plus six IPv6 transition tools, all on the existing IPv6
tab as drawer entries, all with REST endpoints, shareable URLs,
Playwright coverage, and a11y assertions matching the v3.4.0 audit
pattern.

## Non-goals

- Multicast tooling — deferred to v3.6.0 per roadmap.
- New top-level tabs.
- New design tokens or CSS custom properties.
- Any change to admin/, settings, or the API authentication layer.
- Any restructuring of the existing tool-drawer pattern.
- Renaming `ul_bit_flipped` (still deferred to v4.0.0).

## Audience

Same as v3.3.0 / v3.4.0 — anyone who needs an IPv6 calculator. The
prefix-planning tools target small-shop admins who need to slice a
delegated prefix; the transition tools target the long tail of
v4-to-v6 migration scenarios still alive in production networks.

## Architecture

Sequential PR fan-out off `release/v3.5.0`, modelled exactly on
v3.3.0's PR1–PR7 and v3.4.0's PR1–PR12. Each tool is its own PR; all
merge into `release/v3.5.0`; final release-cut PR opens
`release/v3.5.0 → main`.

The `embedded-v4` detector lands **before** the per-scheme decoders so
new tools can call into shared per-scheme detection helpers from day
one. NAT64/DNS64 lands second-to-last because it builds on the existing
`mapped6` (v3.4.0) and benefits from having the other transition
schemes' detection helpers in place.

## Carry-over items (from v3.4.0 roadmap drift)

### #1 IPv6 prefix-delegation planner (issue #387)

**Where:** new module `Subnet-Calculator/includes/functions-prefix-plan6.php`,
new drawer entry `data-tool="prefix-plan"` on the IPv6 tab, new endpoint
`POST /api/v1/prefix-plan6`.

**Inputs:** parent prefix (e.g. `2001:db8::/48`), child prefix length,
optional count and start-offset, nibble-align toggle.

**Outputs:** ordered table of allocated child prefixes with first/last
network, the count of `/64`s contained, and free space remaining at the
parent. GMP throughout. Counts overflow → `"2^N"` string form per
`calculate_subnet6()`.

**Outcome:** small-shop admin can slice a delegated `/48` into
nibble-aligned `/56`s without spreadsheet math.

### #2 IPv6 nibble-boundary helper (issue #388)

**Where:** add to `functions-prefix-plan6.php` (same module — both tools
share nibble-rounding math); drawer `data-tool="nibble"`; endpoint
`POST /api/v1/nibble6`.

**Inputs:** any IPv6 prefix.

**Outputs:** nearest nibble-aligned prefix lengths above and below; the
prefix expressed at each; the count of `/64`s contained at each;
explainer of why nibble alignment matters (DNS reverse zone delegation
and easier mental math).

### #3 RFC 3531 sparse-allocation guidance (issue #389)

**Where:** new module `functions-rfc3531.php`; drawer
`data-tool="rfc3531"`; endpoint `POST /api/v1/rfc3531`.

**Inputs:** parent prefix, total reservation length, allocation strategy
(Centermost / Leftmost / Rightmost).

**Outputs:** ordered list of next-allocation positions per the chosen
strategy, a visualisation of the reservation tree, and the resulting
child prefixes. Composes with the prefix-delegation planner — same
parent prefix, different allocation order.

**Outcome:** networks that grow can keep their prefix tree balanced
rather than fragmenting.

## Transition items (originally v3.5.0)

### #4 IPv6 embedded-v4 detector (issue #390)

**Where:** new module `functions-embedded-v4.php`; drawer
`data-tool="embedded-v4"`; endpoint `POST /api/v1/embedded-v4`.

**Inputs:** any IPv6 address.

**Outputs:** detection of:
- IPv4-mapped (`::ffff:0:0/96`) — defers to `mapped6` (v3.4.0).
- IPv4-compatible (`::/96`, deprecated) — flags as deprecated.
- 6to4 (`2002::/16`) — defers to `6to4` (#6).
- Teredo (`2001::/32`) — defers to `teredo` (#7).
- NAT64 well-known (`64:ff9b::/96`) and NSP — defers to `nat64` (#5).
- ISATAP IID (`::0:5efe:V4ADDR` / `::200:5efe:V4ADDR`) — defers to
  `isatap` (#8).

**Architecture:** acts as the "what is this address?" front door. Each
per-scheme drawer remains the single source of truth for full decoding;
the detector returns scheme + extracted IPv4 + a deep-link to the
relevant drawer.

### #5 NAT64 / DNS64 helper (issue #391)

**Where:** **extends the existing `mapped6` drawer** (v3.4.0) rather than
creating a parallel drawer — `mapped6` already covers `64:ff9b::/96`.
New mode toggle on the existing drawer; new helpers in
`functions-mapped6.php` (or split into `functions-nat64.php` if file size
forces it during implementation). New endpoint `POST /api/v1/nat64`.

**Inputs:**
- v4 → v6: IPv4 address + NAT64 prefix (well-known or custom) + prefix
  length (`/96`, `/64`, `/56`, `/48`, `/40`, `/32` per RFC 6052 §2.2).
- v6 → v4: NAT64 IPv6 address + prefix length.
- DNS64 mode: IPv4 A record + NAT64 prefix → synthetic AAAA per RFC 6147.

**Outputs:** synthesised IPv6 / extracted IPv4 / synthetic AAAA, plus
validation (refuse private IPs from being mapped under the well-known
prefix per RFC 6052 §3.1).

**Risk:** existing `mapped6` Playwright coverage must keep passing
unchanged — additions only, no regressions.

### #6 6to4 address tool (issue #392)

**Where:** new module `functions-6to4.php`; drawer `data-tool="6to4"`;
endpoint `POST /api/v1/6to4`.

**Inputs:** public IPv4 address (v4→v6 mode) or any `2002::/16` address
(v6→v4 mode).

**Outputs:** `2002:WWXX:YYZZ::/48` 6to4 prefix; or extracted public
IPv4 plus surrounding subnet/host bits.

**Validation:** reject private/reserved/multicast IPv4 inputs (6to4 only
works with public unicast). Help text notes RFC 7526 deprecation.

### #7 Teredo address decoder (issue #393)

**Where:** new module `functions-teredo.php`; drawer `data-tool="teredo"`;
endpoint `POST /api/v1/teredo`.

**Decode:** extract Teredo prefix (`2001:0::/32`), server IPv4 (bits
32–63), flags (bits 64–79 incl. cone/restricted-NAT flag), obfuscated
UDP port (bits 80–95, XOR `0xFFFF`), obfuscated client IPv4 (bits
96–127, XOR `0xFFFFFFFF`).

**Encode:** server v4 + client v4 + port + flags → Teredo address.

**Help text** notes operational status.

### #8 ISATAP interface-ID helper (issue #394)

**Where:** new module `functions-isatap.php`; drawer `data-tool="isatap"`;
endpoint `POST /api/v1/isatap`.

**v4 → ISATAP IID:** `::0:5efe:V4ADDR` for non-globally-unique IPv4;
`::200:5efe:V4ADDR` for globally-unique IPv4. Concatenate with any /64
prefix to form a complete ISATAP address.

**ISATAP IID → v4:** recognise the `0000:5efe` / `0200:5efe` pattern,
extract embedded IPv4, decide which form was used.

### #9 6rd address tool (issue #395)

**Where:** new module `functions-6rd.php`; drawer `data-tool="6rd"`;
endpoint `POST /api/v1/6rd`.

**Inputs:** 6rd IPv6 prefix, 6rd IPv4 prefix length, customer IPv4
address (v4→v6 mode); or 6rd IPv6 address + SP parameters (v6→v4 mode).

**Outputs:** customer's delegated IPv6 prefix (concat 6rd IPv6 prefix
with non-masked bits of customer IPv4), or extracted customer IPv4.

### Sequencing rationale

- **Embedded-v4 first (T2)** — the detector is the front door for the
  per-scheme drawers; landing it first means each per-scheme PR
  immediately wires its detection back to the unified entrypoint.
- **Transition tools before prefix-planning tools (T3–T7 before T8–T10)**
  — the transition theme has tighter inter-tool coupling (shared v4
  embedding/extraction primitives), so they cluster well; prefix
  planning is more self-contained and lands cleanly afterward.
- **NAT64/DNS64 last in the transition cluster (T7)** — modifies the
  existing `mapped6` drawer (v3.4.0). Landing after the new transition
  drawers are in place keeps the test surface stable while `mapped6`
  changes are absorbed.
- **Bulk endpoint expansion + a11y audit batched (T11)** — same shape
  as v3.4.0's T10/T11; one pass over all 9 new endpoints is cheaper
  than per-tool a11y/bulk PRs.

## Risks

1. **Transition tools target a long tail of legacy schemes** (Teredo,
   6to4 deprecated, ISATAP largely Windows-only). **Mitigation:** help
   text on each drawer documents operational status with RFC citations
   so users aren't surprised; tools are correctness-tested even where
   real-world deployment is rare.
2. **NAT64 RFC 6052 prefix lengths are unusual** (`/96`, `/64`, `/56`,
   `/48`, `/40`, `/32`). The bit-shuffling rules at non-`/96` lengths
   leave bits 64–71 zeroed — easy to get wrong. **Mitigation:** unit
   tests for every prefix length using the RFC 6052 §2.4 example
   addresses.
3. **Twelve PRs vs v3.4.0's twelve.** Same scope shape, same
   ~2-3-week cycle estimate. **Mitigation:** the 9 issues are
   independently mergeable; if scope pressure lands mid-release, the
   natural cut points are #9 (6rd is the deepest niche), #10 (RFC
   3531 — pure operational guidance), or #11 (a11y audit can split off
   if needed — but that would compromise the audit-on-every-drawer
   invariant inherited from v3.4.0; **prefer dropping a tool over
   dropping the audit**).
4. **NAT64 PR (T7) modifies existing `mapped6`.** Risk of regression in
   v3.4.0 functionality. **Mitigation:** existing `mapped6` Playwright
   tests must pass unchanged; new behaviour is mode-toggled, not
   replacing.
5. **Embedded-v4 detector deep-links to per-scheme drawers** — if a
   per-scheme drawer's URL or shape changes mid-release, the detector
   breaks. **Mitigation:** per-tool URL routes are already locked from
   v3.4.0 (T7); detector lands first (T2) and references those routes;
   any later renames in T3–T7 must update the detector in the same PR.

## Out of scope

- Multicast tooling (RFC 4291 scope, RFC 3956 embedded-RP, RFC 3306
  unicast-prefix-based) → v3.6.0 per roadmap.
- PMTU helper → v3.6.0 per roadmap.
- Renaming `ul_bit_flipped` (breaking API change → v4.0.0).
- New top-level tabs.
- New design tokens.
- Any IPv4 tools — v3.5.0 is purely IPv6.
- Removing the legacy `?tab=&tool=` query-string URL form (back-compat
  invariant from v3.4.0 T7).
