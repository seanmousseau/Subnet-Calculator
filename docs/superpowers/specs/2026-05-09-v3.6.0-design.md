## Goal

Ship four IPv6 multicast tools — scope decoder (the front door),
unicast-prefix-based / SSM, embedded-RP, and a PMTU helper — all on
the existing IPv6 tab as drawer entries, all with REST endpoints,
shareable URLs, Playwright coverage, and a11y assertions matching the
v3.5.0 audit pattern.

## Non-goals

- New top-level tabs.
- New design tokens or CSS custom properties.
- Any change to admin/, settings, or the API authentication layer.
- Any restructuring of the existing tool-drawer pattern.
- Renaming `ul_bit_flipped` (still deferred to v4.0.0).
- `templates/layout.php` per-tool partial extraction — real refactor,
  not patch material; defer.

## Audience

Same as v3.3.0–v3.5.x: anyone who needs an IPv6 calculator. Multicast
tools target network operators handling MLD, embedded-RP rendezvous,
SSM channels, and tunnel/PMTU sizing — niche but well-bounded use cases
that close the IPv6 surface area.

## Architecture

Sequential PR fan-out off `release/v3.6.0`, modelled on v3.3.0–v3.5.x
exactly. Each tool is its own PR; all merge into `release/v3.6.0`;
final release-cut PR opens `release/v3.6.0 → main`.

The **multicast scope decoder lands first** as the front door —
`decode_multicast()` becomes the universal entry point for any
`FF00::/8` address, returning scope + flags + group ID + scheme hint
(SSM / embedded-RP / well-known group / generic). The deeper tools
(T3 SSM, T4 embedded-RP) deep-link back to the decoder, mirroring how
T2 embedded-v4 detector worked for the v3.5.0 transition cluster.

## Multicast tools

### #3 Multicast scope decoder (issue #396, T2)

**Where:** new module `Subnet-Calculator/includes/functions-multicast6.php`,
new drawer `data-tool="multicast"` on the IPv6 tab, new endpoint
`POST /api/v1/multicast6`.

**Inputs:** any IPv6 address (validated as `FF00::/8` or rejected).

**Outputs:** structured decode of:
- **Scope** (RFC 4291 §2.7 + RFC 7346): interface-local (1), link-local
  (2), admin-local (4), site-local (5), organization-local (8), global
  (E), reserved scopes.
- **Flags** (4 bits at offset 8 from prefix): `0RPT` —
  - T (transient): 0 = well-known, 1 = transient.
  - P (unicast-prefix-based per RFC 3306): when set, group is in
    unicast-prefix-based form (T3's domain).
  - R (embedded-RP per RFC 3956): when set, group has embedded RP
    address (T4's domain).
- **Group ID** (low 112 bits — interpretation depends on flags).
- **Scheme hint** (`well-known` / `ssm` / `embedded-rp` / `transient` /
  `reserved`) with a `detail_route` deep-link to T3/T4 when applicable.
- **Recognised well-known groups** (RFC-assigned multicast addresses):
  all-nodes (`FF02::1`), all-routers (`FF02::2`), MLDv2 listeners
  (`FF02::16`), NTP (`FF05::101`), etc. — small built-in registry.

**Outcome:** Operator pastes any multicast address, gets a structured
"what is this?" answer with deep links to the per-scheme decoders.

### #4 SSM / unicast-prefix-based multicast (issue #398, T3)

**Where:** new module `Subnet-Calculator/includes/functions-ssm6.php`,
new drawer `data-tool="ssm"` on IPv6 tab, new endpoint
`POST /api/v1/ssm6`.

**Modes:**
- **Encode**: given a unicast prefix (e.g. `2001:db8::/32`), scope, and
  group ID, build the multicast group:
  - Long form: `FF3x:00LL:PPPP:PPPP:PPPP:PPPP:GGGG:GGGG`
    (LL = prefix length 0..64, PPPP = unicast prefix in network order,
    GGGG = group ID).
  - SSM short form when prefix length is 0: `FF3x::GGGG:GGGG`.
- **Decode**: given a `FF30::/12` (P-flag set) address, extract scope,
  prefix length, unicast prefix, and group ID.

**Validation:** prefix length must be 0..64 (RFC 3306 §6); reject
otherwise.

**Outcome:** SSM channel allocation and decode without spreadsheet
math; composes with T2 multicast scope decoder via deep-link.

### #5 Embedded-RP multicast (issue #397, T4)

**Where:** new module `Subnet-Calculator/includes/functions-embedded-rp6.php`,
new drawer `data-tool="embedded-rp"` on IPv6 tab, new endpoint
`POST /api/v1/embedded-rp6`.

**Modes:**
- **Encode**: given an RP IPv6 address, RIID (4-bit interface ID), scope,
  and group ID, build the embedded-RP multicast group:
  - Form: `FF7s:0RIID:RPPP:RPPP:RPPP:RPPP:GGGG:GGGG`
    where the s=7 marker (R+P+T flags) indicates embedded-RP, RIID
    selects the RP's `::RIID` interface ID, RPPP captures the RP's /64
    prefix in slots 2–5.
  - Constraint: RP prefix length must be 0..64.
- **Decode**: given an `FF70::/12` (R-flag set) address, extract RP
  prefix, RIID, scope, group ID. Compose RP IPv6 = RP-prefix + `::RIID`.

**Validation:** RP-prefix-length and RIID consistency per RFC 3956.

**Outcome:** Build/decode embedded-RP groups for protocols that need RP
discovery without external state.

### #6 IPv6 PMTU helper (issue #399, T5)

**Where:** new module `Subnet-Calculator/includes/functions-pmtu6.php`,
new drawer `data-tool="pmtu"` on IPv6 tab, new endpoint
`POST /api/v1/pmtu6`.

**Inputs:**
- Path MTU (bytes).
- Payload size (bytes).
- Optional extension header list (HBH, routing, fragment, dest-opts).

**Outputs:**
- **Minimum link MTU enforcement**: flag any PMTU < 1280 (RFC 8200 §5).
- **Header overhead**: 40-byte fixed IPv6 header + extension header
  bytes.
- **Effective payload room** = PMTU − header overhead.
- **Fragmentation breakdown** (when payload > effective room): number
  of fragments, fragment offset values (multiples of 8), M-bit values,
  per-fragment payload sizes. Per RFC 8200, fragmentation is end-host
  only — surface that note in the help text.

**Outcome:** "How many fragments?" + "Why is my throughput bad?" + "Is
1280 enough?" all answerable in one tool.

### Sequencing rationale

- **Scope decoder first (T2)** — front door for the per-scheme tools;
  landing it first means T3 and T4 immediately wire deep-links back. Same
  pattern as v3.5.0's embedded-v4 detector.
- **SSM before embedded-RP (T3 → T4)** — SSM's bit layout is simpler
  (P-flag set, no R, RIID is zero); embedded-RP layers more flag bits
  and RIID semantics on top. Easier to get SSM right first, then build
  on it.
- **PMTU last (T5)** — fully independent of T2–T4 (no multicast
  involvement). Lands cleanly even if T2–T4 reschedule.
- **A11y + bulk batched (T6)** — same pattern as v3.5.0 T11. One pass
  over the 4 new endpoints + the v3.5.0 a11y test gaps.

## Risks

1. **Multicast addressing has many edge cases** — reserved scopes, the
   `FF00::/16` (deprecated/reserved) range, the
   `FF00::/12` − `FFF0::/12` flag combinations. **Mitigation:** scope
   decoder validates strictly (any non-`FF00::/8` rejects); flag
   inspection drives the scheme hint precisely so unknown bit
   combinations surface as `reserved` rather than misclassified.
2. **RFC 3306 ↔ RFC 3956 flag overlap** — both set the T flag (0xN1),
   RFC 3306 sets P (0xN3), RFC 3956 sets P+R (0xN7). The scope-decoder's
   scheme-hint logic must distinguish these correctly. **Mitigation:**
   table-driven flag inspection in T2; T3/T4 explicit `flag === 7` /
   `flag === 3` checks before parsing scheme-specific fields.
3. **PMTU helper has minimal IPv6-specific logic** — most of it is
   header-arithmetic. **Mitigation:** keep the tool tightly scoped to
   IPv6 (40-byte fixed header + extension headers), don't drift into
   ICMPv6 PMTU-discovery semantics. Surface RFC 8201 in help text but
   don't implement it.
4. **Seven PRs vs v3.5.0's 12.** Smaller release. **Mitigation:** none
   needed — smaller is good.
